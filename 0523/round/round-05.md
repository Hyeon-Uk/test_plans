# Round 05 — "메모리 증가" 브랜치 분석 (클라이언트 struct std::string)

측정일 2026-06-05 · x86_64 에뮬레이터. 태스크의 "메모리가 증가하거나 미미한 변화" 분석 요구에
따라, round-01에서 유일하게 **증가**로 기록된 항목(클라이언트 struct char*→std::string,
notimem 3000 기준 VmData +44%)을 **실사용 보유량**에서 재검증한다.

## 1. 왜 증가했나 (원인)
struct `_notification`의 15개 문자열 멤버가 `char*`(8B) → `std::string`(~32B, SSO 인라인)으로
커짐. 대부분의 노티는 다수 멤버가 비어 있는데, **빈 std::string도 32B**라 noti당 객체 크기가
~360B 증가. 이는 C→C++ 소유권/안전성(누수·double-free 차단) 전환의 의도된 비용.

## 2. 실사용 보유량 측정 (notimem: title+content+icon 채운 노티 N개 보유)
| 보유 N | BEFORE(char*) VmData | AFTER(std::string) VmData |
|---:|---:|---:|
| 1  | 600 kB | 600 kB |
| 10 | 600 kB | 600 kB |
| 50 | 732 kB | 732 kB |
| (참고) 3000 | 2712 kB | 3900 kB |

→ **N=1~50에서 VmData 완전 동일**. 증가(+44%)는 **N=3000 합성 극단부하에서만** 나타남.
실제 앱은 보통 수~수십 개만 보유 → struct 차이(~396B×50≈20KB)가 VmData 페이지(KB) granularity와
프로세스 baseline에 흡수되어 **관측 가능한 증가 없음**.

## 3. 최적화 판단
- 실사용에서 비용이 0이므로 추가 최적화의 실익 없음.
- 줄이려면 (a) 희소 멤버를 포인터/지연할당 sub-struct로 분리, (b) 일부 멤버 char*+RAII 회귀 —
  모두 **방금 완료해 integ/smoke로 검증된 안전성 마이그레이션을 침습적으로 되돌리는** 변경이라
  회귀 위험이 실익(실사용 0)을 크게 초과 → **net-negative, 미적용**.

## 4. 종합 결론
실사용 기준 **메모리 증가 항목 없음**(클라 동일) + **데몬 대폭 절감**(esd 동적 −80%, 총 PSS −37%
@25라운드, round-04). 즉 리팩토링+최적화 이후 메모리 사용률은 어떤 실사용 시나리오에서도
악화되지 않으며, 데몬에서 25% 기준을 명확히 초과한다.
